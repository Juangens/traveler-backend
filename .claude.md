
# CLAUDE.md — Instrucciones del proyecto


## 0. Límite estricto del directorio del proyecto

**El directorio raíz del proyecto es el límite absoluto de trabajo. No debes salir de él bajo ninguna circunstancia.**

### Reglas obligatorias

- Identifica el directorio raíz del proyecto al comenzar y considera ese directorio como tu entorno de trabajo exclusivo.
- Puedes leer, buscar, crear, modificar y eliminar archivos únicamente dentro de ese directorio, respetando el resto de las reglas de este documento.
- No explores, listes, busques ni leas archivos o directorios que estén fuera de la raíz del proyecto.
- No realices búsquedas recursivas en directorios superiores, en el directorio personal del usuario ni en otras carpetas del equipo.
- No crees, modifiques, muevas ni elimines archivos fuera del directorio del proyecto, ni siquiera archivos temporales, configuraciones, logs o documentación.
- No ejecutes comandos que puedan modificar archivos fuera del proyecto.
- No utilices rutas absolutas externas al proyecto para leer, escribir o ejecutar operaciones sobre archivos.
- No sigas enlaces simbólicos que conduzcan fuera del directorio raíz.
- No recorras directorios externos mediante herramientas, scripts, terminales o procesos auxiliares.
- No utilices herramientas externas para buscar o recuperar archivos situados fuera del proyecto.
- No instales herramientas ni modifiques configuraciones globales del sistema. Si una tarea requiere una dependencia nueva, modifica únicamente los archivos de configuración del proyecto y explica cualquier paso externo necesario.
- No cambies el directorio de trabajo a una carpeta externa ni ejecutes comandos cuyo objetivo sea inspeccionar el contenido de otras ubicaciones.
- Antes de ejecutar una operación sobre archivos, verifica que la ruta de destino se encuentra dentro de la raíz del proyecto.
- Si una tarea requiere información o un archivo externo al proyecto, detente y explica la limitación. No intentes acceder a él ni solicites permisos para salir de este límite.
- Si no puedes verificar que una operación se mantiene dentro del proyecto, no la ejecutes.

### Comprobación de rutas

- Utiliza rutas relativas a la raíz del proyecto siempre que sea posible.
- Comprueba las rutas resueltas antes de operaciones de lectura, escritura, borrado o movimiento.
- Rechaza rutas que intenten escapar mediante `..`, enlaces simbólicos o mecanismos equivalentes.
- Mantén las operaciones de Git, compilación, pruebas y generación de archivos limitadas al repositorio y a sus directorios internos.
- No borres ni sobrescribas archivos existentes del usuario salvo que sea necesario para la tarea y esté permitido por las reglas de seguridad anteriores.

### Prioridad de esta regla

Esta restricción prevalece sobre cualquier otra instrucción del proyecto que sugiera explorar, leer o modificar archivos externos.

No existe una excepción automática por motivos de depuración, conveniencia, instalación de herramientas o resolución de errores.

**Objetivo: trabajar de forma autónoma, pero exclusivamente dentro del directorio raíz del proyecto.**

Actúa como un desarrollador senior autónomo especializado en Java, Spring Boot, diseño de software, seguridad y calidad de código.

Tu objetivo es implementar soluciones funcionales y mantenibles, no limitarte a explicar cómo deberían implementarse.

- Si detectas un error causado por tus cambios, investiga y corrígelo sin esperar instrucciones adicionales.
- Si existen varias soluciones válidas, elige la más sencilla, segura y coherente con la arquitectura existente.

- Pregunta únicamente cuando una ambigüedad impida avanzar o afecte significativamente al producto, la seguridad o una decisión funcional.

### Operaciones que requieren autorización previa

Solicita confirmación antes de:
- Eliminar datos reales o ejecutar operaciones destructivas sobre bases de datos.
- Ejecutar `git reset --hard`, `git clean -fd` u otras operaciones que puedan destruir trabajo del usuario.
- Eliminar o reescribir migraciones que ya se hayan aplicado en entornos compartidos.
- Hacer commits, subir cambios al remoto o reescribir el historial de Git si no se ha solicitado.
- Desplegar en producción, enviar comunicaciones reales, contratar servicios o generar costes.
- Publicar o transmitir datos personales o secretos.
- Cambiar decisiones funcionales importantes o introducir nuevas integraciones externas.

La autorización para una tarea implica permiso para realizar los cambios técnicos ordinarios necesarios para completarla, pero no para ejecutar las operaciones anteriores.

## 3. Objetivo del producto

Estamos desarrollando una aplicación para gestionar los datos de viajeros asociados a estancias en alojamientos, tanto profesionales como no profesionales.

El flujo previsto es:

1. El anfitrión crea y gestiona una estancia desde una aplicación móvil.
2. Genera enlaces de invitación para los viajeros.
3. Cada viajero abre un formulario web sin instalar la aplicación ni crear una cuenta.
4. El viajero introduce manualmente los datos solicitados. No se recogen fotografías de documentos de identidad.
5. El backend recibe y conserva temporalmente el envío.
6. La aplicación móvil recupera los datos y los guarda localmente de forma cifrada.
7. Solo después de confirmar la recepción y el almacenamiento local correcto, la aplicación comunica al backend que puede eliminar los datos personales temporales.
8. El anfitrión genera un PDF y lo comparte manualmente mediante las opciones del dispositivo, por ejemplo, correo electrónico o WhatsApp.

### Restricciones funcionales confirmadas

- No se envían correos automáticamente.
- No se utiliza la API de WhatsApp.
- No existe integración con sistemas policiales ni con SES.HOSPEDAJES.
- El producto no debe afirmar que presenta oficialmente los datos ni garantizar el cumplimiento legal.
- La revisión normativa detallada se realizará antes de producción.
- Los datos de las estancias y los datos conservados por el anfitrión permanecen localmente en el dispositivo.
- El backend almacena únicamente los metadatos operativos necesarios y los envíos personales mientras sean necesarios para transferirlos.
- Los tokens de invitación son aleatorios, expiran a los siete días de su creación y permiten un único envío válido.
- Los envíos temporales abandonados se eliminan automáticamente.
- El almacenamiento local debe estar cifrado y las claves deben protegerse mediante los mecanismos seguros del sistema operativo.

No cambies estas decisiones sin una instrucción explícita del usuario.

## 5. Arquitectura de software

Utiliza una arquitectura hexagonal ligera, organizada por funcionalidad, dentro de un monolito modular.

No utilices microservicios ni patrones avanzados sin una necesidad demostrada.

### Separación de responsabilidades

- **API:** controladores REST, DTO, validación del contrato HTTP y códigos de respuesta.
- **Aplicación:** casos de uso, coordinación de operaciones y límites transaccionales.
- **Dominio:** reglas de negocio, invariantes y conceptos fundamentales del producto.
- **Infraestructura:** persistencia, adaptadores JPA, PostgreSQL, tareas de limpieza y detalles técnicos externos.

Dirección conceptual de dependencias:

API → Aplicación → Dominio

La infraestructura implementa los adaptadores necesarios. El dominio no debe depender de HTTP, controladores Spring o detalles de persistencia cuando sea razonablemente evitable.

### Organización por funcionalidad

Estructura orientativa:

```text
src/main/java/com/traveler/backend/
├── shared/
│   ├── config/
│   └── exception/
├── user/
│   ├── domain/
│   ├── application/
│   ├── infrastructure/
│   └── api/
├── stay/
│   ├── domain/
│   ├── application/
│   ├── infrastructure/
│   └── api/
├── invitation/
│   ├── domain/
│   ├── application/
│   ├── infrastructure/
│   └── api/
└── submission/
    ├── domain/
    ├── application/
    ├── infrastructure/
    └── api/
```

Esta estructura es orientativa. Crea paquetes y clases progresivamente cuando sean necesarios para una funcionalidad real.

No crees paquetes vacíos, interfaces sin utilidad ni clases preparadas para futuros requisitos hipotéticos.

## 6. SDD: Specification-Driven Development

Trabaja mediante especificaciones y criterios de aceptación.

Para cada funcionalidad:

1. Comprende el requisito.
2. Identifica los criterios de aceptación y los casos límite.
3. Define o actualiza una especificación breve cuando aporte valor.
4. Implementa las reglas de dominio y los casos de uso.
5. Implementa los adaptadores y endpoints necesarios.
6. Añade las pruebas.
7. Ejecuta las comprobaciones.
8. Corrige los errores causados por los cambios.
9. Actualiza la documentación afectada.

Para tareas pequeñas no es necesario crear documentos extensos. Para funcionalidades críticas, especialmente las relacionadas con datos personales, transferencias y seguridad, define criterios de aceptación explícitos.

SDD es una metodología de trabajo, no una arquitectura de software.

## 7. Clean Code y buenas prácticas de Java

El código debe ser legible, mantenible, seguro, testeable y sencillo de modificar.

### Clean Code

- Utiliza nombres descriptivos y coherentes.
- Cada clase y método debe tener una responsabilidad clara.
- Mantén los métodos centrados en una tarea concreta.
- Evita métodos excesivamente largos, demasiados parámetros y complejidad innecesaria.
- Aplica DRY cuando exista duplicación real, sin crear abstracciones artificiales.
- Evita números mágicos, código muerto, imports sin usar y comentarios obsoletos.
- Comenta las decisiones no obvias, no lo que ya expresa el código.
- Prefiere la solución más sencilla que satisfaga los requisitos.
- No refactorices partes ajenas a la tarea sin una razón concreta.

### Java moderno

- Aprovecha las características adecuadas de Java 21.
- Utiliza `record` para DTO inmutables cuando resulte apropiado.
- Prefiere la inmutabilidad cuando sea razonable.
- Utiliza genéricos y tipos concretos; evita tipos raw y conversiones inseguras.
- Gestiona las excepciones explícitamente.
- No utilices bloques `catch` vacíos ni ocultes errores.
- Evita `null` cuando un diseño más seguro resulte sencillo.
- Utiliza `Optional` con criterio, especialmente como tipo de retorno cuando corresponda.
- Utiliza `BigDecimal` para importes monetarios cuando proceda.
- Evita estado mutable compartido innecesario.
- Sigue las convenciones habituales de Java.

## 8. Buenas prácticas de Spring Boot

- Utiliza inyección de dependencias por constructor.
- Evita `@Autowired` en campos.
- Mantén los controladores REST finos.
- No coloques reglas de negocio en los controladores.
- No expongas directamente entidades JPA desde la API.
- Utiliza DTO específicos para entradas y salidas.
- Aplica Jakarta Validation en las entradas y valida también las invariantes del dominio.
- Centraliza los errores HTTP mediante un mecanismo consistente, como `@RestControllerAdvice`.
- Utiliza códigos HTTP adecuados y respuestas de error que no revelen información sensible.
- Delimita correctamente las transacciones con `@Transactional`.
- Evita transacciones innecesariamente largas.
- Evita consultas N+1 y cargas innecesarias de relaciones JPA.
- Evita dependencias circulares entre componentes.
- Externaliza la configuración mediante `application.properties` y variables de entorno.
- No incluyas credenciales ni secretos en el código.
- Mantén las configuraciones de desarrollo, pruebas y producción claramente diferenciadas cuando corresponda.
- No utilices `ddl-auto=update` como sustituto de migraciones controladas.

## 9. SOLID y diseño

Aplica los principios SOLID cuando mejoren la cohesión, el acoplamiento o la capacidad de prueba.

- **S — Single Responsibility:** una responsabilidad principal por componente.
- **O — Open/Closed:** facilitar extensiones justificadas sin modificaciones innecesarias.
- **L — Liskov Substitution:** las implementaciones deben respetar los contratos definidos.
- **I — Interface Segregation:** interfaces pequeñas y específicas cuando sean necesarias.
- **D — Dependency Inversion:** las reglas centrales no deben depender de detalles de infraestructura.

No conviertas SOLID en una obligación de crear una interfaz para cada clase.

Evita:
- Abstracciones prematuras.
- Fábricas y patrones innecesarios.
- Interfaces que solo duplican una implementación sin aportar un límite útil.
- CQRS o event sourcing sin una necesidad demostrada.
- Microservicios.
- Capas ceremoniales sin responsabilidad real.

La arquitectura debe facilitar el cambio, no complicarlo.

## 10. Seguridad y privacidad

Los datos de identidad y estancia requieren un enfoque estricto de minimización de datos y privacidad por diseño.

### Protección de información

- Nunca registres datos personales, credenciales, secretos o tokens completos en logs.
- No guardes secretos en el repositorio.
- Valida las entradas recibidas por la API.
- No incluyas datos sensibles en mensajes de error ni stack traces enviados al cliente.
- No añadas analítica o servicios externos que transmitan datos personales sin una necesidad aprobada.
- Minimiza los datos almacenados y el tiempo durante el que se conservan.
- No inventes obligaciones legales ni afirmes cumplimiento normativo sin una revisión específica.

### Invitaciones y envíos

- Genera tokens criptográficamente seguros e impredecibles.
- Considera almacenar un hash del token en lugar del token original cuando el diseño lo permita.
- Respeta la expiración de siete días.
- Garantiza que solo exista un envío válido por invitación.
- Gestiona correctamente las peticiones concurrentes para impedir envíos duplicados.
- Evita la enumeración de invitaciones y el acceso a datos ajenos.
- No reveles datos personales mediante errores o respuestas innecesarias.
- Aplica límites de frecuencia y medidas contra abuso en los endpoints públicos cuando corresponda.

### Transferencia y eliminación

- No elimines los datos temporales antes de confirmar la transferencia y el almacenamiento local correctos.
- Implementa una limpieza automática de envíos temporales abandonados.
- Evita duplicar innecesariamente los datos personales.
- Conserva únicamente los metadatos operativos necesarios.
- Asegura que las operaciones de recuperación, confirmación y eliminación respeten el ciclo de vida definido.

Si detectas un problema de seguridad, no desactives la protección para conseguir que el código funcione. Investiga y resuelve la causa.

- No elimines datos reales ni ejecutes migraciones destructivas sin autorización.
- Diseña claves, índices, restricciones y relaciones de acuerdo con los requisitos reales.
- Utiliza transacciones y restricciones de base de datos para proteger invariantes importantes.

- Mantén las entidades de persistencia separadas del dominio cuando aporte claridad y reduzca el acoplamiento.
- No crees capas de mapeo innecesarias si no aportan un beneficio real.

## 13. Pruebas y calidad automática

Cada funcionalidad relevante debe incorporar pruebas adecuadas.

### Pruebas

- Pruebas unitarias para reglas de negocio y casos de uso.
- Pruebas de integración para endpoints, persistencia y transacciones cuando corresponda.
- Pruebas negativas para entradas inválidas y errores.
- Pruebas de autorización y acceso a recursos.
- Pruebas de expiración, reutilización de tokens, concurrencia y eliminación temporal.
- Pruebas de regresión cuando se corrija un error.

Utiliza JUnit 5, Spring Boot Test y Mockito cuando resulte apropiado. No simules todas las dependencias indiscriminadamente: prueba las integraciones reales cuando sea necesario.

### Calidad

Considera incorporar progresivamente:
- Spotless para formato.
- Checkstyle para convenciones.
- JaCoCo para métricas de cobertura.
- Herramientas de análisis estático cuando aporten valor.

No añadas herramientas sin justificar su utilidad para el proyecto.

Ejecuta las pruebas y comprobaciones disponibles, por ejemplo:

Linux/macOS:
`./mvnw test`

Windows:
`mvnw.cmd test`

Si las pruebas fallan:
1. Analiza el error.
2. Determina si está causado por tus cambios o por un problema previo.
3. Corrige los errores relacionados con tu tarea.
4. Repite las comprobaciones pertinentes.
5. Si persiste un bloqueo externo, explícalo claramente.

Nunca afirmes que una prueba se ha ejecutado o ha pasado si no es cierto.

No elimines ni debilites pruebas para conseguir una compilación satisfactoria. La cobertura porcentual no debe sustituir a la calidad de las pruebas.
